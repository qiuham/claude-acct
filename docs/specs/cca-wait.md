# `cca wait` —— 等额度重置后自动续上会话

关联：`design.md`（命令面与解析）、`explicit-profile.md`（账号显式化：号要写出来）、
`openrouter.md`（选型）。本文只写"等待-继续"这一块。

状态：已实施（2026-10-03）。实施中改掉了两处原设计的事实错误，见 §3 与 §6 的"实测修正"。

## 1. 背景与目标

额度撞墙时（`001` 的 5 小时窗口跑满 → `Usage limit reached`），会话会停在半路：面板上还显示
`working`，但请求已经发不出去。使用者要守到重置时刻，再手动打一句"继续"。

目标：**一条命令把这件事挂起来**。

```bash
cca wait 001 --detach --prompt 继续      # 到 001 的窗口重置时，把它那时卡住的会话逐条续上
```

成功判据三条：不用使用者守着；错过时刻（机器重启、进程被杀）也能补跑；**不打断真在跑的会话**。

## 2. 事实基础（全部实测）

* **重置时刻是现成数据**：`cca ls --json` 的 `usage.windows.{five_hour,seven_day}.resets_at`
  是 epoch 秒，直接算等待时间，不用猜。
* **面板状态名不可信**：实测四条卡在额度上的 001 会话（`d8cb575d` / `52753a7a` / `f034cc6a` /
  `d22d7a2b`），面板状态**全是 `working`**，而 transcript 尾部带 `usage limit` / `429`。
  所以"该不该推"要按事实判定，不能按状态名。
* **"进程活着"不等于"在干活"**：这四条会话的进程都还活着（`claude logs` 读得到输出），
  按"日志还在流动 → 真在跑"会把停着的会话全判成在跑、一条都不推（实测踩过）。
* **文件 mtime 也不等于"在干活"**：`f034cc6a` 被额度卡住后，监控任务仍每半分钟往它队列里写一条
  `queue-operation`，mtime 一直很新；拿 mtime 判"还在写"同样会误判（实测踩过）。
  真正的判据是**最后一条对话记录自己的时间戳**（见 §3），记账类记录一律不看。
* **续一条会话的原语**：按**短 job id** `cca <号> stop <短id>`（清挂起登记）+ 在**该会话自己的
  cwd** `cca <号> -p "<提示>" --resume <完整会话id>`（实测能给已有会话追加一轮）。
  实测修正：`claude stop` **只认面板上的短 job id**（`claude agents --json` 的 `id`），
  给它完整会话 UUID 会回 `No job matching` —— 登记没清掉，接下来的 resume 只会拿到
  `running as a background session`，一条都推不动（原设计写成 `stop <会话id>`，是错的）。
* **这台机器没有 systemd 用户会话**：`systemctl --user is-system-running` → `offline`，
  `systemd-run --user` → `Failed to connect to bus`。所以"零操心"只能靠自带的后台进程（`--detach`），
  系统定时器最多作为别的机器上的可选做法写进文档。

## 3. 判定规则：哪些会话该推

**候选**：触发那一刻，`active_workers(<号>)`（该号 daemon 的面板）里**除 `done` 外**的全部会话 ——
`blocked` / `failed` / `idle` / `working` 一视同仁，因为状态名不可信。已经完成的（`done`）不推，
推了是重复劳动。

对每条候选，只看一处事实：**transcript 里最后一条对话记录**（跳过记账类记录；取记录自己的
`timestamp`，不看文件 mtime）。

| # | 事实 | 结论 |
| --- | --- | --- |
| ① | 最后一条对话出现额度/限流字样：`429`、`usage limit`、`You've hit your`、`rate limit` | **卡在额度上 → 推** |
| ② | 没有额度字样，且最后一条对话在**两分钟内**、`claude logs` 显示进程还活着 | 真在跑 → **跳过**，留到下一轮，不 stop、不打断 |
| ③ | 没有额度字样，且最后一条对话在两分钟内、进程已退出 | 等输入 → **推** |
| ④ | 没有额度字样，最后一条对话在两分钟前（半小时、几小时没动） | 停着等输入 → **推**（进程活着也只是挂着） |
| ⑤ | 拿不到 transcript，或尾部只有记账记录读不出对话 | **保守跳过** + 日志记一行原因，绝不瞎推 |

实测修正：原设计把 ②③ 写成"`claude logs` 显示进程已退出 → 推；日志还在流动 → 跳过"。
真机四条被额度卡住的会话进程全活着（`claude logs` 有输出），按原规则**一条都不会推** ——
所以判据换成"最后一条对话有多新"，进程死活只用来区分 ② 与 ③。

三个开关覆盖例外：`--all`（跳过①②③④⑤，候选全推）、`--only <会话id…>`（只推指定会话）、
`--dry-run`（只打印"现在会推哪几条"与判定依据，不动任何会话）。

**判定发生在触发那一刻**，不在登记时 —— 等待期间新卡住的、已经跑完的，都能得到正确处理。

## 4. 状态与语义

状态文件：`<accounts_root>/waiting.json`，0600，**临时文件 + rename 原子写**（写入过程崩溃不会
留下半个 JSON）。一条记录：

```
{ id, profile, sessions|null, prompt, window(5h|7d|auto), not_before, created_at, state,
  retry_after, results }
```

`retry_after` = 下一次可以重试的时刻（额度没放开时按退避写进去，`--run` 到点才再看这条）。

* `sessions` 为 `null` = "到点按 §3 挑"；给了 id 列表 = 只推这些（显式优先）。
* **幂等**：`sent` / `failed` 算终结，重复 `--run` 不再动它。`results` 每条记
  `state` / `at` / `first_at` / `tries` / `note`。
* **pending 会重试**（评审抓到的 Critical，原实现漏了）：额度还没放开（`retry`）与"会话真在跑"
  （`skipped`）都记 `pending`，下一轮**接着推** —— 少了这条，重置时刻刚到点、窗口还没真放开
  那一次失败会把整条记录永久卡住，`--run` 也永不退出。
* **两条兜底**：单条会话重试超过 `WAIT_RETRY_HORIZON`（1 小时，按该条 `first_at` 算）→ 记 `failed`；
  整条记录从第一次执行算起超过 `WAIT_GIVE_UP_SECONDS`（24 小时）→ 收尾（`failed` + 说明），
  保证 `wait_loop` 最终能退出。
* **每推完一条就落盘、当场说一行**：一轮可能跑几十分钟，中途被 kill 也不会把推过的当没推过；
  落盘前**重新读盘再合并**（保住并发 `--cancel` 掉的、轮内新登记的记录）。
  进度要看得见：`--list` 对正在跑的条目显示"正在推：已出 N 条"并列出已出的逐条结果，
  `--detach` 的日志每推完一条写一行 —— 否则整轮跑完前看起来像"没生效"（使用者实测反馈）。
* **一条坏记录不拖垮整夜**：缺字段的记录、单条会话抛异常（含 `claude logs` 超时）都只标注它自己。
* **补跑（catch-up）**：`not_before` 已过而记录还没跑完的，下一次 `--run` 立刻执行。这是"长期"
  的关键 —— 机器重启、进程被杀、你隔天才回来调一次 `--run`，都还能补上。
* **清理**：**完成时刻**（`finished_at`）超过 7 天的记录在下次 `--run` 时删掉；`--cancel <id>`
  立即删除。落盘只写回**盘上还在**的条目 —— 推一轮可能跑几十分钟，期间被 cancel 掉的
  自己那条不能又被写回去（实测修正：原实现会把它复活，等待器接着推）。

## 5. 命令面

```bash
cca wait <号> [<会话id…>] [--prompt <提示>] [--window 5h|7d|auto] [--at <HH:MM>]
              [--all] [--only <会话id…>] [--dry-run] [--detach]
cca wait --list [--full]            # 列出等待记录；--full 不截断长说明
cca wait --cancel <记录id>
cca wait --run [--once]             # 消费到期的记录；--once 跑一轮就退出
```

细则：

* **不给 `--at`** → `--window auto` 等**挡着你的那个窗口**：只看快到上限（`WAIT_BLOCKING_PERCENT`
  = 95%）且**还没重置**的，5 小时优先、没有看 7 天；快到上限的那个已经重置 → **立刻可跑**。
  百分比只用在这里（挑窗口），不用来判"卡没卡住"（真机 95% 就已被限流）；显式 `--window 5h|7d`
  保持老语义（明说等哪个窗口，不看百分比）。
  实测修正：原设计"取最近一个未来重置"有两个坑 —— 健康的号会白等到重置时刻；5 小时已重置、
  7 天在两天后时会**白等两天**（10-03 真机踩到，只能用 `--at` 绕开）。
* `--at <HH:MM>` = 显式时刻：以现在为基准取**最近的那个未来时刻**（`--at 01:40` 在 23:00 跑就是
  次日 01:40）。这是留给"我就是想那个时候推"的口子。
* `--run` 没有到期的记录时：带 `--once` 直接退出；不带则睡到下一个 `not_before`，队列空就退出。
* `--detach` = 登记后用 `nohup setsid` 起一个 `cca wait --run`，日志写
  `<accounts_root>/wait/<记录id>.log`。**跑的是当前这份脚本的绝对路径，不是 PATH 里的 `cca`** ——
  `cca` 可能指向另一个 checkout 或另一个版本（本机就指着主 checkout），那样等待器跑在**没有
  `wait` 的代码**上：登记成功、到点什么都不发生。不带 `--detach` 就只登记 —— 谁来调 `--run`
  （cron、tmux、你自己）cca 不管。
* 号必须写出来（沿用账号显式化的约定）；`--list` / `--cancel` / `--run` 是全局动作，不带号。
* **`--list` 要能一眼看出"这条登记怎么样了"**（使用者实测反馈：只有一行时看不出 12:00 那条在不在守）：
  渲染成表格（`记录 / 号 / 状态 / 到点 / 说明`，和 `cca ls` 一致；没装钉住版本的 Rich 时退到纯文本，
  不许直接死）。还没跑的排在前面，每条给 **倒计时**、**会推什么**（显式列表 / 到点自动挑）、
  **提示词**、**现在这一眼会推哪几条**（`wait_targets()` 的结果，标注"到点按那时的事实重判"）、
  **有没有等待器在守**（读 `/proc` 找 `cca wait --run`，没守要明说 —— 不带 `--detach` 就只是登记、
  到点不会有人动它）、**日志路径与最后写入时刻**；跑完的给逐条结果（`sent` 绿 / `failed` 红 /
  `pending` 黄），长说明默认截到 88 字符，`--full` 看全文。
* `--detach` 起的等待器带 `PYTHONUNBUFFERED=1`：日志是文件时 stdout 默认块缓冲，
  "睡到几点"那行会一直卡在缓冲区里，从外面看就是"日志空的、不知道它在不在守"（实测踩到）。

## 6. 执行一条会话的路径

**只有 §3 判定为"该推"的会话才会走到这里** —— 判为"真在跑"（分支 ②）与"读不出对话"
（分支 ⑤）的既不 stop 也不 resume，留到下一轮再看。

```
job=$(查该号面板：这条会话的短 job id)          # `claude stop` 只认它
比对 claude logs <job> 两次（隔 8 秒）           # 还在动 = 真在跑 → 跳过，不 stop（stop 会掐掉在跑的任务）
cca <号> stop <job>                             # 清后台登记（本来没登记就不停）
cd <该会话自己的 cwd>                            # 从 cca sessions --all --json 里查
cca <号> --bg --resume <完整会话 id> "<提示>"    # 追加一轮，并把会话**挂回面板**
```

实测修正（10-06 真机）：原设计用 `cca <号> -p "<提示>" --resume <id>`，那是**前台**跑 —— 会话在面板里
消失、跑完才回来，使用者既看不到进度（"到底推没推"），中途自己去 `--bg --resume` 还会被 fork 成
**副本**（`note: session … is open in another Claude Code process, so this started a copy as …`）。
改成 `--bg --resume`：会话重新登记回该号面板，一边跑一边能 `cca <号> attach <短id>` 看。

代价与对策：`--bg` 立刻返回 `backgrounded …`，**光看输出分不出额度放开没有** —— 所以挂回去之后
还要盯一会儿（`WAIT_BG_VERIFY_SECONDS` = 45 秒）：transcript 里出现新的对话 → `sent`；
新的对话是额度/限流错误 → `retry`（退避重试照旧）。另外同批里只要有一条撞回额度，剩下的直接记
pending 留到下一轮（窗口没放开，再推也是撞墙）。

登记的会话 id 可以是短 id（`--dry-run` 显示的就是它）：到点推之前先补成完整 UUID
（先问面板，面板里没了就查共享会话池）—— 实测修正：不补的话 `--resume <短id>` 直接报
`--resume requires a valid session ID`，一条都推不动（10-03 真机踩到）。

真机实测（2026-10-03，ds 号上一次性的后台会话）：

* 登记还在时直接 resume → 被拒：`Error: That session is running in the background (73b08e60).
  Run `claude attach 73b08e60` to open it, or `claude stop 73b08e60` first to resume it here.`
  —— 所以 **stop 是必须的**，而且必须给短 job id（给完整 UUID 回 `No job matching`）；
* 按短 job id stop 之后，同样的 `-p --resume` 成功追加一轮（transcript 里出现新的
  `assistant` 记录），会话随即从面板消失（这是"追加一轮"，不是重新挂成后台会话）；
* 四条被额度卡住的 001 会话，`claude logs` 输出 6 秒内逐字节相同 —— 日志是否还在动
  可以当"真在跑"的临门一脚判据（包括那条还在收监控通知的 `f034cc6a`）。

输出分类：

* 挂回面板后 45 秒内看到额度字样 → **5 分钟退避重试**，同一条最多重试到"距 not_before 1 小时"为止
  （窗口放开时间可能比快照晚几分钟）；同批剩下的也跟着留到下一轮；
* 命中 `running in the background`（CLI 拒绝原文见上）→ 记 `skipped`，下一轮再看（说明它真的在跑）；
* 日志还在动 → 记 `skipped`，这一轮不碰它；
* 其它非零退出 → 记 `failed` + 输出末尾 200 字，继续下一条（一条坏了不影响别的）；
* 成功 → 记 `sent`。

**逐条串行**：刚重置的窗口很薄，并发推会互相抢；串行也让日志可读。

**为什么现在又是 `--bg --resume`**：`--bg` 立刻返回、看不出额度放开没有，这个缺点已经用
"挂回去之后盯 45 秒看 transcript"补掉了；而 `-p` 的缺点（会话从面板消失、看不到进度、
使用者中途 resume 会 fork 副本）没法补。两条权衡下来选可见的那条。

## 7. 非目标

* **不做周期/每天**（`--every` 之类）：只解决"等这次额度"。
* **不做常驻守护**（没有 `cca waitd` 轮询）：`--detach` 起的进程完成任务就退出。
* **不在别的 cca 命令里偷跑**：`cca ls` 只多显示一行"N 条等待中（cca wait --list）"，
  绝不替你在后台起会话（`cca doctor` 不查等待记录）。
* **不替你改写提示词**：`--prompt` 给什么推什么。默认是
  `额度已重置，继续刚才中断的工作。` —— 光写"继续"它可能读成"使用者允许了"，而不是
  "额度窗口已重置"（实测反馈），所以默认句同时说出原因与对象。
* **不跨号**：一条记录只属于一个号。

## 8. 验证

离线（不联网、不花额度，`tests/test_claude_acct.py`）：

1. **触发时刻**：喂一份 `cca ls --json` 的 fixture（5 小时卡住 / 7 天卡住 / 都没卡三种），断言算出的
   `not_before` 与说明；`--at 01:40` 的"最近未来时刻"取舍（含跨天）；
2. **判定分支**：造 transcript（额度字样 / 记账记录噪声 / 只有记账记录 / 刚写过 / 半小时没动 /
   进程已退出 / 文件缺失），断言挑出哪几条、跳过哪几条，以及 `--dry-run` 的输出；
3. **幂等**：同一条记录跑两次 `--run`，第二条不再推（假 `claude` 桩的调用次数）；
4. **补跑**：`not_before` 设为 1 小时前、记录仍是 waiting → `--run` 立刻执行；
5. **重试退避**：桩返回额度错误 → 记录 `skipped/pending`，并把 `retry_after` 写成 5 分钟后的时刻
   （测试里不真等，直接断言这个字段）；
6. **被后台登记占住**：桩返回 CLI 的拒绝原文 → 记 `skipped`；
7. **推之前的闸**：日志还在动 → 不 stop 不 resume（断言桩没收到这两条命令）；静止 → 先按短
   job id stop、再用完整会话 id resume；
8. **`--list` / `--cancel`**：列出与删除；`--cancel` 之后 `--run` 不再碰它；
9. **`--detach`**：断言起的进程参数与日志路径正确（桩住 `setsid`/`nohup`，不真起进程）；
10. **原子写**：状态文件权限 0600；写入用 tmp + rename（断言目录里不留 `.tmp`）。

真机验收：

* **判定**（2026-10-03 00:40）：`cca wait 001 --dry-run` 对当下四条卡在额度上的 001 会话
  （`52753a7a` / `d8cb575d` / `f034cc6a` / `d22d7a2b`）全部给出"推"，依据分别是"最后一条对话是
  额度/限流错误"与"最后一条对话在 68–264 分钟前，进程活着也只是停着"；
* **原语**（2026-10-03 00:5x，ds 号）：见 §6 的三条实测记录（拒绝原文、stop 后 resume 成功、
  日志静止可当判据）；
* **端到端**（重置时刻那一次）：见 §10。

## 9. 与现有东西的关系

* 今晚临时写的一次性脚本 `~/.local/bin/cca-continue-at` 由本功能取代；脚本可以留着救急，
  但文档不再推荐，`cca wait` 是正式入口。
* 复用既有设施：额度快照（`cca ls --json`）、会话清单（`resumable_sessions()` / `active_workers()`）、
  transcript 尾部读取（`last_session_model()` 的读法）、`require_profile()`、
  清单/状态文件的 0600 + 原子写模式。
